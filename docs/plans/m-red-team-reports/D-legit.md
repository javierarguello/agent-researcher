# D-legit — cost and waste inside the ceiling / LEGITIMATE USER

## Verdict for the surface: held by accident
The ceiling ($20, both Florida modes) never touches an honest job (est. $2.6 today, $3.9 real pre-C4 → 5–8× headroom) and never touches the harness's worst spend payload either (plan-spam × all 10 producers = +$0.46 est., 2.3% of it) — what actually bounds waste is `maxIterations = 2·budget+6`, and that bound is a NUMBER, not a property: it already cuts honest, diligent agents (8 of 10 Florida producers in the mock; three agents at the bound in the two real July traces) before their paid budget is spent, and it is invisible in the trace.

## Findings (most severe first)

### F1 · `maxIterations = 2·budget+6` cuts honest, diligent producers before their paid budget — 13 of 92 turns never spent, and the cut is invisible
- where: `packages/core/src/engine/gather.ts:172` (`const maxIterations = maxTurns * 2 + 6`), `:187` (every iteration — plan, cached fetch, budget-reached refusal, nudge — counts against it), `:96-101` + `research-engine.ts:755` (`gatherCompleted`: `stalled` is not reusable), and nowhere (`GatherStop` reaches no note, no trace field, no summary).
- input: no attacker. An honest agent that does what the prompts say — `update_plan` first, "then again as you learn" (`gather.ts:21`), "(3) revise the plan as you learn" (`prompt.ts:363`), one tool per turn, and re-reads pages a peer already fetched (cached, free — the shared evidence store's whole point; the deep-dive-refiner's focus text says "fetch_page listing URLs for details still marked n/a", which the deal-scout fetched).
- observed (mock, Florida comprehensive, honest fake web): plan-once → 92/92 turns, no agent at the bound. Re-plan-per-step → **79/92 turns; deal-scout 22/24 (54/54 iterations), valuation-analyst 7/10 (26/26), deep-dive-refiner 7/10 (26/26), compliance 7/8, community 7/8, financial 5/6, risk 4/5, market-refiner 4/5 — 8 of 10 at the bound, none concluded**. Loop chars 5.07M vs 3.41M. Not one note or field says so: `stalled` is computed and dropped.
  Corroboration in the two REAL July traces (`out/*/trace.json`, gemini-2.5-flash): the model re-plans ≈ once per step (market-analyst 7 plans/6 turns, deal-scout 23/21 and 24/24, compliance 8/6); **deep-dive-refiner run 1: 22 plans + 4 cached re-reads + 0 paid turns = 26 tool notes = its bound exactly (budget 10 → 26)** — it hit the ceiling of iterations before its first search; **risk-analyst run 1: 16 plans, 0 turns = its bound (budget 5 → 16)** — a plan-loop with no attacker; **deal-scout run 2: 24+24+6 = 54 = its bound**. So the real model already lives at this bound; plan-spam is a heavier version of what an honest run does by itself.
- what it changes: (a) what the buyer receives — the deep-dive-refiner in real run 1 wrote its "pro pass" from zero new searches, deal-scout in the mock leaves 2 of its 24 listings turns unspent; (b) what we spend — a stalled loop is non-reusable, so ONE flaky write afterwards re-buys it: **18 turns billed for a 10-turn budget** (measured; the retry stalls again, only its searches are re-paid because its pages are now cached) vs 10 when the loop had concluded; (c) what we store — nothing records the stop reason, so an admin reading the July trace cannot see that two agents never researched.
- status: **reproduced** (mock: `d-legit.test.ts :: 2 · … re-planning after every step … 79 of 92 turns; 8 of 10 producers hit maxIterations`, and the `it.fails` PROPERTY test; `3 · … STALLS AGAIN: 18 turns billed for a 10-turn budget`), **corroborated** by reading the real traces (reasoned: notes are per tool call; 26 = 26 and 16 = 16 are not coincidences when the budget was unspent).
- refutation attempted: (1) Is one-tool-per-turn realistic, or does Gemini batch plan+tool in one call (halving iterations)? The July notes show plans ≈ turns+1 and two loops ending EXACTLY at their bound with budget left — batching would have left them under it. (2) Is the stall harmless because the write proceeds anyway? Yes for the section — until the write hiccups once (18 vs 10 turns), and yes only if the evidence lost to the cut did not matter (real run 1's deep-dive-refiner: it did — zero new searches for the pass the buyer paid the "pro" premium for). (3) Does anything else terminate an honest plan-loop? No: `update_plan` returns `{ok, turnsLeft}` with no "stop planning" signal; the nudge fires only when there are NO tool calls.
- fix sketch (2 lines): count free iterations (plan / cached fetch / budget-reached refusal) on their own allowance derived from the budget (e.g. plans ≤ budget+2, cached reads ≤ 2×targetCount) and answer the excess with a tool result that says "stop planning: search or write" — and write `GatherStop` into a note. What a legit request would lose if fixed NAIVELY: raising the bound (so honest re-planners finish) lets plan-spam run longer, unless the loop is bounded by CHARS instead; lowering it (D-attack's direction) turns 8/10 honest stalls into 10/10 and cuts deeper into paid budgets.

### F2 · `turnsUsed` under-counts a loop that threw — the buyer's progress line, the summary and the admin's per-agent row show fewer turns than were billed
- where: `research-engine.ts:747-748` (`counter.turns += gres.turns; trace.turnsUsed = gres.turns` — AFTER `gather` returns; a throw inside the loop skips both) vs `gather.ts:273-274` (the turn and `searchCost` are charged to the sink BEFORE the call).
- input: one transient provider error (`503`) on the scout's third loop call, after plan + one search.
- observed: scout `cost.searchCalls` 3, `turnsUsed` 2; job `cost.searchCalls` 5, `turnsUsed` 4. Money right (sink), count wrong. `summary.turnsUsed`, `progress.turnsUsed`, admin `JobDetail` agent rows read the wrong one.
- status: **reproduced** — `d-legit.test.ts :: 3 · … a 503 in the LOOP … the trace UNDER-COUNTS: turnsUsed 4 while searchCalls is 5`.
- refutation attempted: does anything reconcile from `searchCalls`? No — `turnsUsed` is its own field everywhere it is shown. Is it just the retry-waste test's territory? That file counts web calls, not `turnsUsed`.
- fix sketch: have `gather` report turns through the sink (or a `turns` callback) as it spends them, like cost. Legit loss: none.

### F3 · The flagship denominator everyone cites is inflated by a fixture defect: `context-size.measure.test.ts` loses `charts` and counts the failed calls
- where: `packages/core/test/context-size.measure.test.ts:22,63` (PROSE 1,600 chars into every string) vs `src/templates/chart.ts:13` (`description: z.string().max(500)`) → chart-analyst fails write + repair × 2 attempts; the run reports `completed` and the test asserts only status, so `meta.sections = [{charts, lost}]` goes unnoticed. Its "794.2k write chars" includes 8 chart-analyst rows ≈ 417k of failed calls; the honest write total with a valid chart is **538k** (15 writes, largest 67.4k).
- status: **reproduced** (my sampler respects `maxLength`; the honest comprehensive run then completes with `meta.sections = []`; the stock run does not — asserted in `2 · … plan once …`).
- refutation attempted: is `.max(500)` reachable by an honest model? Yes — it is our schema; the point is only that the measurement was measuring retries. Not a product defect; it matters because it is the number D-attack's "2.84×" and "×N" are compared to.
- fix sketch: `sampleFromSchema` honours `maxLength`; the measure test asserts `meta.sections` empty. Legit loss: none.

## Checked and found sound (so nobody re-reports it)
- Evidence reuse across attempts INSIDE a dispatch when the loop ended `done`: +1 generate call, +0 turns for one flaky write (mutation `ctx.research.done = false` at `research-engine.ts:755` → +5 calls, +2 turns; described, not executed — shared checkout).
- Loop request size grows linearly with turns (deal-scout 24 turns: largest 47–49k chars; 8-turn agents: 15–23k) — page bodies are trimmed to `KEEP_FULL_PAGES`; the fake corpus's ~1k pages cannot show the 6k-page effect, the July pre-C4 trace can (deal-scout 1.92M input tokens over ~46 iterations).
- Search cost, not LLM, is the larger honest line at Tavily rates: $1.63 vs $0.95 est. for comprehensive; the ceiling is 5–15× away from every honest mode.
- Handoffs ≤ 1,500 chars each (13 × 1.5k = 19.5k in the checkpoint), checkpoint pages ≤ 60 × (6,000 + note), slim agent traces carry no notes; everything of size is GCS (`uploadJson`), Firestore holds progress (one line, ≤ ~16k chars worst), cost, summary (errors sliced 500/300), headline.
- Essential vs comprehensive: 40 vs 92 turns, 8 vs 10 producers — D1's figures reproduce; est. all-in $1.31 vs $2.58.
- The harness reach-table rows are essential-mode numbers (budgets 2/2, maxIterations 10 per producer) — the red-team model declares no modes and the harness passes none. Worth saying once so nobody scales them as comprehensive.
- Query length is bounded by the provider (400/422) and the budget; no amplification (agrees with D-attack).
