# C-legit — surface C (model output → what the buyer sees / what we store) / LEGITIMATE-USER lens

## Verdict for the surface: held by accident
The viewer's prose links are safe only because react-markdown's default `urlTransform` happens to be on (nothing in our code asks for it), and the PDF's `mdInline` is "safe" by being so narrow that it already breaks honest citations (query strings, parentheses, `mailto:`) and flattens Markdown the prompt explicitly asks for (numbered lists, tables). None of C-attack's proposed defences would cost an honest Florida report anything today EXCEPT an `https`-only allowlist copied from the PDF into the viewer (kills `mailto:`) and hiding `progress.message` outright (kills the one line that shows the buyer the research happening).

## Findings (most severe first)

### F1 · The PDF double-escapes `&` in every cited URL — a listing link with a query string is broken in the artifact the buyer keeps
- where: `packages/core/src/pdf/report-html.ts:124-125` — `mdInline` runs `esc(s)` on the whole string FIRST, then the link regex captures the already-escaped URL and calls `esc(u)` on it AGAIN.
- input: prose `Asking $450,000 per [the listing](https://www.bizbuysell.com/Business-Opportunity/laundromat-miami/2201234/?utm_source=search&ref=list).`
- observed: `href="https://…?utm_source=search&amp;amp;ref=list"` — the browser decodes one level and follows `?utm_source=search&amp;ref=list`; the second parameter is named `amp;ref`. Every real BizBuySell/LoopNet/BizQuest URL with more than one query param is affected; the directive (`prompt.ts:50-54`) tells the model to cite "the actual URLs from the evidence".
- status: reproduced (`packages/core/test/red-team/c-legit.test.ts::a listing URL with a query string is DOUBLE-ESCAPED`, `it.fails` — red against today's code)
- refutation attempted: checked whether `esc()` is idempotent (it is not: `&amp;` → `&amp;amp;`); checked whether the browser/Chrome PDF printer un-escapes twice (it does not, HTML entities decode once); checked the viewer path (react-markdown does not have this bug — the same link works on screen, so the buyer sees it work on the web and fail in the PDF).
- fix sketch: capture the link BEFORE escaping (tokenise links, escape text, then emit `<a href="${esc(rawUrl)}">`), or un-escape `u` before re-escaping. A legit request loses nothing.

### F2 · The PDF cuts a URL at its first `)` — Wikipedia/Census-style paths lose their tail; and `mailto:` broker contacts print as literal brackets
- where: `packages/core/src/pdf/report-html.ts:125` — `\((https?:\/\/[^\s)]+)\)`.
- input: `[the city profile](https://en.wikipedia.org/wiki/Hialeah,_Florida_(city))` and `Contact [the listing broker](mailto:broker@example-brokerage.test) to request the CIM.`
- observed: `href="https://en.wikipedia.org/wiki/Hialeah,_Florida_(city"` (trailing `)` left in the running text; the link 404s or lands on a disambiguation page). The `mailto:` line renders as the raw text `Contact [the listing broker](mailto:broker@example-brokerage.test) to request the CIM.` — in the web viewer the SAME field is a working `mailto:` link (react-markdown's `safeProtocol` allows `mailto`), so the two artifacts disagree.
- status: reproduced (`c-legit.test.ts::a Wikipedia-style URL with parentheses is CUT`, `::a mailto: broker contact is a link in the web viewer and LITERAL BRACKETS in the PDF` — both `it.fails`, red today)
- refutation attempted: does the model ever write parenthesised URLs? Wikipedia/`census.gov` (`…/table?q=(…)`) do occur in market sections; the honest fixture corpus has none, so this is reasoned-plausible, mechanism reproduced. `mailto:` — the directive says "cite evidence as links using actual URLs from the evidence"; a broker email is on most listing pages, so a model writing it is legitimate, not an attack.
- fix sketch: allow one level of balanced parens (`(?:[^\s()]|\([^\s()]*\))+`) and add `mailto:` to the PDF regex — matching react-markdown's set (`https?|mailto`) so screen and PDF agree. Nothing legit is lost. Note for C-attack: if a viewer allowlist is added, it must include `mailto:` or the viewer regresses to the PDF's behaviour.

### F3 · The PDF flattens the Markdown the prompt asks for: a NUMBERED list becomes one paragraph; a GFM table prints as raw pipes
- where: `packages/core/src/pdf/report-html.ts:131-146` (`mdToHtml` handles only `-`/`*` bullets and `#` headings) vs `packages/core/src/engine/prompt.ts:50-54` (`MARKDOWN_DIRECTIVE`: "Use it — **emphasis**, bullet/numbered lists, short sub-headings").
- input: `Three steps:\n\n1. Request the CIM.\n2. Verify the lease to 2031.\n3. Confirm SBA eligibility.` and `| Business | Asking |\n|---|---|\n| Sunshine Coin Laundry | $450,000 |`
- observed: `<p>1. Request the CIM. 2. Verify the lease to 2031. 3. Confirm SBA eligibility.</p>` and `<p>| Business | Asking | |---|---| | Sunshine Coin Laundry | $450,000 |</p>`. The viewer (remark-gfm) draws both correctly (viewer test pins the table inside a `risks` item).
- status: reproduced (`c-legit.test.ts::a NUMBERED list … is flattened`, `::a GFM table in a prose field is printed as raw pipes` — `it.fails`, red today)
- refutation attempted: is `1.` maybe caught by the bullet regex? No — `/^\s*[-*]\s+/` only. Does the mock/honest run ever produce numbered lists? The scripted mock writes LOREM; the live model is INVITED to by the directive, so this is a directive/renderer disagreement, not a model quirk. Tables are not invited but are the most common Markdown a model reaches for when comparing listings.
- fix sketch: add an `<ol>` branch (`/^\s*\d+[.)]\s+/`) and either a minimal pipe-table branch or drop "numbered lists" from the directive and say "no tables". A legit report loses nothing either way; today it loses structure silently in the artifact it forwards.

### F4 · The buyer's live progress line is English with internal schema keys, whatever language they bought — 11/17 lines on a `language: es` run
- where: `packages/core/src/engine/research-engine.ts:344` (`emit`), `:737/:764/:795` (`Researching (…)`, `Writing (…)`, `Composing (…)` interpolate SECTION KEYS), `gather.ts:257/306/340/367` (`Plan updated (N steps).`, `Searched: <query>`, `Reused cached page.`, `Fetched N page(s).`); written verbatim by `run-job.ts:314` → `setProgress`; shown verbatim by `apps/fbizlab/src/pages/JobView.tsx:76`.
- input: `runResearch(redTeamModel, { subject: 'lavanderías en venta', location: 'Miami-Dade County, FL', language: 'es' })` with the plain mock.
- observed: 17 progress messages; 11 match an English template (`Searched|Fetched|Writing|Composing|Researching|Reused|Plan updated|Suggested sources`); 5 carry a raw section key (`Researching (findings).`, `Writing (findings).`, …). Sample: `Starting workflow [essential]: 3 agents (0 already done).`, `Wave 1/3: scout.`, `Researching (findings).`, `Plan updated (1 steps).`, `Searched: test query`. For the Florida model the buyer reads `Writing (market_overview, competitive_landscape).` mid-run. `report-copy.ts:123-127` already states the rule for THIS line ("rendered raw by the client, so it has to be the buyer's language and must not name an internal limit") and localises only the `held` case.
- status: reproduced (`c-legit.test.ts::a language: es job writes ENGLISH progress messages` and `apps/fbizlab/test/red-team-c-legit.test.tsx::what a Spanish buyer actually gets from the engine today` — both `it.fails`, red today)
- refutation attempted: does JobView localise or map the message? No — it prints `job.progress.message` raw; the API (`apps/api/src/index.ts:1492/1535`) passes it through. Does the manifest step label cover it? Partly: `step.label`/`step.description` ARE localised from the manifest and shown above the message — that is the middle ground.
- fix sketch: keep the localised phase label + a small localised note table keyed by note KIND (`searched`, `fetched`, `writing`) with the query as the only interpolation; never interpolate section keys (use section TITLES from the template if named at all). What a naive "hide `progress.message`" loses: `Searched: <query>` — the one line that shows the buyer the research happening (viewer test pins that both the localised phase and the message render today; the mutation that hides the message reds it). C-attack's `progress-note` payload rides the same field; the kind-keyed table closes both.

### F5 · The ready email deletes `&` from an honest headline: "Bed & Breakfast inns for sale" arrives as "Bed  Breakfast inns for sale" in the HTML body (subject keeps it)
- where: `packages/core/src/email/templates.ts:183` — `title.replace(/[<>&]/g, '')` (strip, not escape); the subject at `:189` uses the unstripped title.
- input: `reportReadyTemplate('FBizLab', 'Bed & Breakfast inns for sale — Key West, FL', url, 'en')`
- observed: subject `…— Bed & Breakfast inns for sale — Key West, FL`; HTML body `<strong>Bed  Breakfast inns for sale — Key West, FL</strong>`. Same title, two spellings in one email. "M&A", "B&B", "Bar & Grill", "Wash & Fold" are ordinary Florida business headlines.
- status: reproduced (`c-legit.test.ts::"Bed & Breakfast" arrives as "Bed  Breakfast"`, `it.fails`, red today)
- refutation attempted: is `&` needed for safety? No — `&` alone is not markup; escaping to `&amp;` is the safe AND faithful option. `<`/`>` stripping is fine (a headline never legitimately needs them).
- fix sketch: `esc()` the title into the HTML (`&`→`&amp;`, `<`→`&lt;`) instead of deleting; keep the raw title in subject/text. Nothing legit lost.

### F6 (minor) · `tel:` in prose renders as a DEAD link in the viewer (`<a href="">`), not as text and not as a working link
- where: react-markdown default `safeProtocol = /^(https?|ircs?|mailto|xmpp)$/i` behind `apps/fbizlab/src/components/ReportViewer.tsx:115-116`.
- input: `Call [the broker](tel:+13055550123) to schedule a walkthrough.`
- observed: `{ text: 'the broker', href: '' }` — styled as a link, goes to the current page. Same for `javascript:` (which is the GOOD half: it is why C-attack's prose-`javascript:` claim is refuted).
- status: reproduced (`red-team-c-legit.test.tsx::a tel: broker number becomes a DEAD link today`, `it.fails`)
- fix sketch: a `urlTransform` that returns the URL for `https?|mailto|tel` and, for anything else, drops the anchor to plain text (custom `a` component: if `!href` render `children` only). If a viewer allowlist is added for the raw `href={…}` sites, use the same set.

## Checked and found sound (so nobody re-reports it)
- **Images**: no honest input produces a Markdown image. `MARKDOWN_DIRECTIVE` asks for links only; the honest fake-web corpus and the mock LLM contain no `![`; the Florida `charts` section is `z.array(chartSchema)` (structured `ChartSpec`) rendered by recharts (viewer) / `chartSpecHtml` (PDF), never `<img>`. Stripping `img` from react-markdown (viewer/admin/read page) costs a Florida report nothing today; the viewer test pins that `<img>` DOES render now (the red→green test for the fix) and that a chart renders with zero `<img>`. If a future model wants logos/photos, the allowlist would need a same-origin or signed-URL rule, not a Markdown image.
- **`javascript:` in PROSE links** (viewer): neutralised by react-markdown's default `urlTransform` (`href=""`); reproduced. C-attack's remaining raw-`href` sites (`ReportViewer.tsx:220/230/321`, `report-html.ts:252/289/314`) are the real ones; the PDF's `mdInline` already restricts prose to `https?`.
- **`http://`, ports, IDN hosts, non-ASCII paths, `%`-encoded paths**: all survive both `mdInline` (PDF) and react-markdown (viewer) — pinned in both files. A naive `https`-only rule would break `http://` legacy listing pages; the tests name that mutation.
- **Sources labels**: `label = s.title || s.url` (Florida `derive`, `florida-business-for-sale.ts:769-775`); Brave/Tavily populate `title`. Nothing truncates it today; a 130-char real listing title renders whole (pinned). C-attack's "cap at N chars" would cut real titles — the URL fallback only fires on an empty title.
- **`askingPrice: null`**: viewer and PDF both skip the tile (`isNum`), print no `null`, no `$0`, no `[object Object]`, and still show the revenue tile (pinned in both).
- **180-char business name**: rendered whole in both (no `clip()` on the deal name; `clip` is only on the transactions table's description column, by design).
- **`[object Object]`**: not reproducible from an honest report through `ReportViewer`/`buildReportHtml` — every `String()` site is guarded (`typeof === 'string'`, `isNum`, `ObjectFields` for objects). Round 6's instance was `run-local.ts`/`directives` in the mandate table, already fixed (`report-html.ts:484`).
- **`risks` item with a GFM table**: viewer draws a `<table>` inside the `<li>` (pinned); PDF prints pipes (F3).
- **Progress line phase label**: `JobView` already shows the MANIFEST step label/description in the report's language above the raw message — the middle ground exists (pinned).
